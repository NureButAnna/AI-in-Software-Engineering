# Реалізація одного зрізу PaperTrail

Специфікація ЛР1 у lab1/docs/ — єдине джерело правил. Не змінюй її, щоб спростити патч.
Шляхи lab1/docs/ і lab2/ — від кореня репозиторію; references/ — від теки цього Skill.
Усі команди запускай з теки lab2/.

## Розподіл відповідальності (lab1/docs/architecture.md)
- schemas.py — форма вхідних даних: типи, enum, дати, trim, невідомі поля, відсутнє поле проти null;
- services.py — бізнес-правила: власник запису, переходи статусів, кінцевий статус, фільтрація,
  транзакції; не знає про HTTP і FastAPI;
- models.py, database.py — таблиці SQLAlchemy, підключення SQLite (з увімкненими зовнішніми ключами);
- routes.py — токен → користувач, виклик сервісу, доменна помилка → HTTP-відповідь.
Розміщуй кожну зміну в шарі, якому вона належить.

## Процедура
1. Визнач зріз (A–E) за запитом. Якщо запит охоплює кілька зрізів, запропонуй
   розділити роботу й почни з одного.
2. Знайди зріз у references/slices.md і прочитай лише зазначені там розділи lab1/docs/.
3. Перелічи перевірки: критерії приймання (AC) та сценарії T-xx, яких стосується зміна.
4. Дай план із 3–5 пунктів і дочекайся підтвердження.
5. Внеси мінімальну зміну лише в дозволених для зрізу файлах, разом із тестами
   для сценаріїв із кроку 3.
6. Перед запуском перевір свій diff: якщо він працює з файлами поза tmp_path,
   з мережею, запускає процеси або видаляє дані — зупинись і дочекайся підтвердження.
7. Запусти перевірки з теки lab2/:
   python -m pytest -q
   python -m ruff check app tests --select E4,E7,E9,F,I
   Якщо щось падає — виправ код і запусти знову. Після двох невдалих спроб
   зупинись і опиши ймовірну причину: далі діагностує людина.
8. Наведи фактичний підсумок перевірок і окремо — що не зроблено або потребує
   рішення людини.

## Заборони
- Не змінюй маршрути, поля й коди відповідей, визначені в lab1/docs/api-contract.md.
- Не додавай і не оновлюй залежності; не змінюй налаштування середовища.
- Запускай лише команди перевірки з кроку 7.
- Наявні тести змінюй, лише якщо вони суперечать контракту, і поясни чому;
  не видаляй перевірки й не пропускай тести, щоб вони пройшли.
- Не додавай функцій поза обсягом ЛР1: маршрути для задач, документів, файлів, установ і
  нагадувань (їх лише попередньо описано в реєстрі API), скидання пароля, OAuth, ролі,
  пагінацію, складний frontend, Docker, хмарне розгортання, AI-витягування (це ЛР4).
- SQL — лише через ORM або параметризовані запити; тести — лише на тимчасовій базі (tmp_path).
- Не стверджуй, що перевірки пройшли, не запустивши їх. Рішення прийняти зміну — за людиною.

## Формат відповіді

що не зроблено.
