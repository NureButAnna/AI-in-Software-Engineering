# PaperTrail — API Contract (Крок 7, ЛР1)

**Статус:** проєкт для командного погодження, не реалізований API  
**Версія:** `0.2-draft`  
**Дата:** 15.11.2026  
**Основне джерело:** `requirements.md` (версія з `change_log.md`, 59 AC), розділи *User Stories і критерії приймання — Release MVP* та *Контракт даних і бізнес-правил*  
**Методичне джерело:** `LR1_Mini_Issue_Tracker_Requirements_Design.docx`, крок 7.  
**Зміни у 0.2:** виправлення за перехресним рев'ю (`traceability-review.md`, знахідки T-01–T-13).

> **Межі цього кроку.** Методичка описує Mini Issue Tracker як навчальний приклад із приблизно 10 API-операціями, проте наданий `requirements.md` описує **PaperTrail** (справи, облікові записи, документи, установи, задачі та нагадування). Тому нижче формалізовано **9 базових операцій PaperTrail** (вихід виконує клієнт без серверного маршруту, F-22) і окремо наведено каталог маршрутів, які знадобляться для решти Release MVP. Не слід вважати ці 9 маршрутів повним API всіх US-01–US-10.
>
> **Умовні позначення:** **[ДЖЕРЕЛО]** — правило вже зазначене в `requirements.md`; **[ПРОПОЗИЦІЯ]** — рішення про HTTP/API, що потребує прийняття командою; **[OPEN]** — неврегульована суперечність або відкрите питання. Наведені відповіді є **проєктними прикладами**, а не результатами запущеного сервера.

## 1. Загальні правила контракту

### 1.1. Протокол та формати

| Параметр | Контракт | Походження |
|---|---|---|
| Стиль | REST поверх HTTP(S), JSON для запитів і відповідей | [ПРОПОЗИЦІЯ] |
| Базовий шлях | `/api/v1` | [ПРОПОЗИЦІЯ]; префікс не встановлено джерелом |
| Формат JSON | `Content-Type: application/json; charset=utf-8` | [ПРОПОЗИЦІЯ] |
| Ідентифікатори | `integer`, додатні, у path `case_id`; невірний тип/формат → `422` | integer ID — [ДЖЕРЕЛО, ПРИПУЩЕННЯ], HTTP → [ПРОПОЗИЦІЯ] |
| Дата | `YYYY-MM-DD`, без часу | [ДЖЕРЕЛО, ПРИПУЩЕННЯ] |
| Часова мітка | ISO 8601 UTC із `Z`, напр. `2026-11-09T15:30:00Z` | [ДЖЕРЕЛО] |
| Авторизація | `Authorization: Bearer <token>`; відсутній/недійсний токен → `401` | захищені операції й токен — [ДЖЕРЕЛО], схема Bearer — [ПРОПОЗИЦІЯ] |
| Межа видимості | Власник визначається з токена; чужий запис повертає **`404`**, як і відсутній | [ДЖЕРЕЛО] + HTTP → [ПРОПОЗИЦІЯ] |
| Відсутній результат списку | `200` та `[]`, не `404` | [ДЖЕРЕЛО] + HTTP → [ПРОПОЗИЦІЯ] |
| Нове створення | `201 Created`, JSON зі створеним записом | [ПРОПОЗИЦІЯ] |
| Читання/успішне оновлення | `200 OK`, JSON з актуальним записом | [ПРОПОЗИЦІЯ] |
| Успішне видалення | `204 No Content`, порожнє тіло | [ПРОПОЗИЦІЯ] |
| Некоректний вміст запиту | `422 Unprocessable Content` з деталями поля; **жодних часткових змін** | безпечна атомарність — [ДЖЕРЕЛО], HTTP → [ПРОПОЗИЦІЯ] |
| Конфлікт із правилом станів | `409 Conflict` і незмінність даних | поведінка — [ДЖЕРЕЛО], HTTP → [ПРОПОЗИЦІЯ] |
| Дублікат email | `409 Conflict`, обліковий запис не створюється | поведінка — [ДЖЕРЕЛО], HTTP → [ПРОПОЗИЦІЯ] |

**Поля, які сервер не приймає від клієнта:** `id`, `owner_id`, `created_at`, `updated_at`, `password_hash` та інші службові/нередаговані поля. Їх включення у тіло створення чи оновлення — `422`. Статус справи під час створення автоматично `PREPARING`, у загальному `PATCH /cases/{case_id}` поле `status` заборонене. [ДЖЕРЕЛО]

### 1.2. Уніфіковані помилки

**[ПРОПОЗИЦІЯ]** Усі помилки повертаються в одній формі:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Некоректні вхідні дані",
    "details": [{ "field": "title", "message": "Назва не може бути порожньою" }]
  }
}
```

| HTTP | `error.code` | Коли застосовується |
|---:|---|---|
| `401` | `AUTH_REQUIRED` | Токен відсутній, прострочений або недійсний; також для невдалого входу `INVALID_CREDENTIALS` |
| `404` | `NOT_FOUND` | Запис відсутній або належить іншому користувачу |
| `409` | `DUPLICATE_EMAIL` / `INVALID_STATE_TRANSITION` | Унікальний email; бізнес-конфлікт переходу статусу |
| `413` | `FILE_TOO_LARGE` | Файл понад 5 МБ; розмір перевіряється раніше за тип (`requirements.md`, розд. 4) |
| `415` | `UNSUPPORTED_FILE_TYPE` | Тип файла не з переліку PDF, JPG/JPEG, PNG, DOCX, TXT, XLSX, P7S |
| `422` | `VALIDATION_ERROR` | Порожнє/недозволене поле, невірні тип, формат, дата, enum; некоректні query/path параметри |

**Важливо:** 404 для чужого й неіснуючого ресурсу навмисно однаковий — API не розкриває існування чужих даних. Жодна помилка не змінює базу даних. HTTP-відповіді та JSON-обгортка — нові проєктні рішення; їх потрібно погодити.

### 1.3. `PATCH`: одне правило для всіх сутностей

API **посилається на розділ «3. Правила часткового редагування»** у `requirements.md`, а не створює нову бізнес-семантику:

- Відсутнє поле → не змінювати. `{"title":"Нове"}` не змінює `deadline`.
- Явний `null` → очистити **лише необов'язкове** поле. Наприклад, `{"deadline":null}`.
- `null` для обов'язкового поля, порожнє тіло `{}`, невідомі або нередаговані поля → `422` **[ПРОПОЗИЦІЯ для HTTP]**.
- Усі передані значення валідовуються до запису; зміна транзакційна, помилка будь-якого поля → rollback без часткових змін.
- Статус змінюється тільки спеціальним маршрутом `PATCH /cases/{case_id}/status`.

### 1.4. Представлення справи (`CaseResponse`)

**[ПРОПОЗИЦІЯ]** Однакова схема у відповідях на створення/перегляд/редагування:

```json
{
  "id": 17,
  "title": "Отримання закордонного паспорта",
  "status": "PREPARING",
  "deadline": "2026-11-30",
  "created_at": "2026-11-09T15:30:00Z",
  "updated_at": "2026-11-09T15:30:00Z"
}
```

`owner_id` не приймається на вході; його можна не показувати клієнтові. `CaseResponse` використовується у списках і у відповідях на створення, редагування та зміну статусу. Деталі справи (API-06) повертають розширену форму `CaseDetailsResponse` з пов'язаними задачами, документами й установами [ДЖЕРЕЛО: AC-04.7, R-04].

## 3. Опис операцій, полів і відповідей

### API-01 — `POST /auth/register`

**Призначення.** Створити обліковий запис з email і паролем; після успішної реєстрації користувач залишається неавторизованим і переходить до входу. [ДЖЕРЕЛО: AC-01.1–01.7]

- **Path/query:** немає. **Auth:** не потрібна.
- **JSON body:** `email: string` (обов'язковий, непорожній, формат email, унікальний); `password: string` (обов'язковий, ≥8 символів, не складається лише з пробілів).
- **Успіх `201`:** `{ "id": 3, "email": "user@example.com", "created_at": "2026-11-09T15:00:00Z" }` (пароль і хеш не повертаються; токен не видається).
- **Помилки:** `422` — некоректний email/пароль, порожні дані, зайві поля; `409` — email уже зареєстрований.
- **Уточнення:** конвертація email у lowercase позначена припущенням у `requirements.md`; конкретний алгоритм хешування не погоджено.

**Приклад запиту:**

```http
POST /api/v1/auth/register HTTP/1.1
Content-Type: application/json

{"email":"user@example.com","password":"examplePass8"}
```

**Приклад помилки:**

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"error":{"code":"DUPLICATE_EMAIL","message":"Користувач із таким email уже існує","details":[]}}
```

### API-02 — `POST /auth/login`

- **Призначення:** перевірити email/пароль і видати сеансовий токен. [ДЖЕРЕЛО: US-02]
- **Path/query:** немає. **Auth:** не потрібна.
- **Body:** `email: string` та `password: string`, обов'язкові.
- **Успіх `200`:** `{ "access_token": "<token>", "token_type": "bearer" }` — форма [ПРОПОЗИЦІЯ].
- **Помилки:** `422` — відсутні/форматно некоректні поля; `401` з `INVALID_CREDENTIALS` — email/пароль не збігаються; не вказувати, що саме не збіглося.
- **[OPEN]:** TTL токена й повторний вхід не визначені джерелом; серверного відкликання токена немає [F-22].

**Приклад:** `{"email":"user@example.com","password":"examplePass8"}` → `200` із токеном.

### API-03 — вилучено

Серверного маршруту виходу немає. Вихід виконує клієнт: видаляє збережений токен і показує екран входу; серверне відкликання токена не виконується [ДЖЕРЕЛО: F-22, AC-02.6, R-12]. Ідентифікатор API-03 повторно не використовується.

### API-04 — `POST /cases`

- **Призначення:** створення справи з `status=PREPARING`. [ДЖЕРЕЛО: US-03]
- **Auth:** обов'язкова. **Path/query:** немає.
- **Body:** `title: string` — обов'язкова непорожня після trim; `deadline: string(date) | null` — необов'язкова, типово `null`.
- **Сервер встановлює:** `id`, `owner_id`, `status=PREPARING`, `created_at`, `updated_at`.
- **Успіх `201`:** `CaseResponse` (§1.4).
- **Помилки:** `401`, `422` (порожня назва, некоректна дата, недозволене `status` чи `owner_id`).

**Приклад успішного запиту:**

```http
POST /api/v1/cases HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"title":"Отримання закордонного паспорта","deadline":"2026-11-30"}
```

**Приклад відповіді `201`:**

```json
{"id":17,"title":"Отримання закордонного паспорта","status":"PREPARING","deadline":"2026-11-30","created_at":"2026-11-09T15:30:00Z","updated_at":"2026-11-09T15:30:00Z"}
```

**Приклад помилки:**

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{"error":{"code":"VALIDATION_ERROR","message":"Некоректні вхідні дані","details":[{"field":"title","message":"Назва не може бути порожньою"}]}}
```

### API-05 — `GET /cases`

- **Призначення:** отримати список лише власних справ; якщо немає справ — `[]`. [ДЖЕРЕЛО: US-04]
- **Auth:** обов'язкова. **Body:** відсутнє. **Path:** немає.
- **Query (усі необов'язкові):** `status` — одне значення enum `PREPARING | SUBMITTED | IN_REVIEW | APPROVED | REJECTED | CANCELLED`; `due` — `overdue` або `upcoming`; `today` — календарна дата користувача `YYYY-MM-DD`, обов'язкова, якщо задано `due`. Фільтри діють окремо або разом за логічним AND; справи без дедлайну не потрапляють у жоден `due`. [ДЖЕРЕЛО: FR-05, AC-04.9, `requirements.md` розд. 5.4–5.5]; назва параметра `today` — [ПРОПОЗИЦІЯ]
- **Успіх `200`:** `CaseResponse[]`; сортування `deadline ASC`, `null` наприкінці, однакові дати — `title` за українською абеткою без урахування регістру, далі `created_at ASC`, незалежно від статусу [ДЖЕРЕЛО: AC-04.3, R-08, розд. 5.3]. Поєднання фільтрів без збігів (наприклад, `status=APPROVED&due=overdue`) → `200` і `[]`.
- **Помилки:** `401`; `422` — невідоме значення `status` чи `due`, невідомий query-параметр, некоректна дата `today` або `due` без `today` [ДЖЕРЕЛО: розд. 5.5; HTTP — ПРОПОЗИЦІЯ].

**Приклад:** `GET /api/v1/cases` → `200` з масивом справ; `GET /api/v1/cases` для користувача без справ → `[]`; `GET /api/v1/cases?status=SUBMITTED&due=overdue&today=2026-11-15` → лише справи `SUBMITTED` із дедлайном до 2026-11-14 включно.

### API-06 — `GET /cases/{case_id}`

- **Призначення:** отримати деталі конкретної власної справи. [ДЖЕРЕЛО: US-04]
- **Path:** `case_id: integer > 0`; **Query/body:** немає. **Auth:** обов'язкова.
- **Успіх `200`:** `CaseDetailsResponse` — поля `CaseResponse` і масиви `tasks` (у порядку створення), `documents` та `institutions` [ДЖЕРЕЛО: AC-04.7, R-04, `architecture.md` §2]; склад полів елементів масивів — [ПРОПОЗИЦІЯ]:

```json
{
  "id": 17,
  "title": "Отримання закордонного паспорта",
  "status": "SUBMITTED",
  "deadline": "2026-11-30",
  "created_at": "2026-11-09T15:30:00Z",
  "updated_at": "2026-11-10T08:00:00Z",
  "tasks": [{ "id": 3, "title": "Сфотографуватися", "is_completed": true }],
  "documents": [{ "id": 5, "title": "Внутрішній паспорт", "received_date": "2015-04-02" }],
  "institutions": [{ "id": 2, "name": "ДМС, відділ № 3" }]
}
```
- **Помилки:** `401`; `404` для чужої/відсутньої справи; `422` для некоректного `case_id`.

### API-07 — `PATCH /cases/{case_id}`

- **Призначення:** змінити лише передані `title` і/або `deadline`. [ДЖЕРЕЛО: US-03; правила PATCH]
- **Path:** `case_id: integer > 0`; **Query:** немає. **Auth:** обов'язкова.
- **Body:** непорожній JSON-об'єкт; дозволено `title: string` (trim, непорожній) та `deadline: YYYY-MM-DD | null`.
- **Успіх `200`:** актуальний `CaseResponse`.
- **Помилки:** `401`; `404` чужа/відсутня справа; `409` редагування заборонено у кінцевому статусі; `422` помилкові дані, `{}`, `status`, `id`, `owner_id` чи інше невідоме поле.
- **Атомарність:** якщо надіслано коректний `title` і некоректний `deadline`, **не змінюється нічого**.

**Приклад запиту:**

```http
PATCH /api/v1/cases/17 HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"title":"Отримання паспорта","deadline":null}
```

**Приклад помилки без часткового оновлення:**

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{"error":{"code":"VALIDATION_ERROR","message":"Некоректні вхідні дані","details":[{"field":"deadline","message":"Некоректна календарна дата"}]}}
```

### API-08 — `PATCH /cases/{case_id}/status`

- **Призначення:** встановити статус окремою операцією; поле запиту лише `status`. [ДЖЕРЕЛО: модель статусів]
- **Path:** `case_id: integer > 0`; **Query:** немає. **Auth:** обов'язкова.
- **Body:** `{ "status": "SUBMITTED" }`, де enum: `PREPARING | SUBMITTED | IN_REVIEW | APPROVED | REJECTED | CANCELLED`.
- **Успіх `200`:** актуальний `CaseResponse`; повторне встановлення того самого статусу → `200`, без зміни `updated_at` [ДЖЕРЕЛО: діагональ матриці].
- **Помилки:** `401`; `404`; `422` невідоме значення статусу, відсутнє/зайве поле; `409` заборонений перехід **відповідно до формалізованої матриці**.

**Приклад успішного запиту:**

```http
PATCH /api/v1/cases/17/status HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json

{"status":"SUBMITTED"}
```

**Приклад забороненого переходу (`PREPARING → APPROVED`):**

```http
HTTP/1.1 409 Conflict
Content-Type: application/json

{"error":{"code":"INVALID_STATE_TRANSITION","message":"Перехід PREPARING → APPROVED заборонений","details":[]}}
```

Перехід перевіряється за матрицею 6 × 6 (`requirements.md`, розд. 2.2); AC-06.1–06.4 їй відповідають, тому OPEN-C01 закрито.

### API-09 — `DELETE /cases/{case_id}`

- **Призначення:** видалити власну справу навіть у кінцевому статусі. [ДЖЕРЕЛО: US-03, розділ 2 та 5]
- **Path:** `case_id: integer > 0`; **Auth:** обов'язкова; **Query/body:** немає.
- **Успіх `204`:** тіло відсутнє.
- **Помилки:** `401`; `404` відсутня/чужа справа; `422` некоректний path ID.
- **Каскади в одній транзакції:** задачі справи видаляються; зв'язки `case_documents` і `case_institutions` видаляються, але самі документи й установи залишаються; нагадування зберігаються, `case_id` стає `null` [ДЖЕРЕЛО: F-17, R-10]. Якщо документ пов'язаний із кількома справами, зв'язки з іншими справами зберігаються.
- **Важливо:** UI-підтвердження видалення, якщо потрібне, реалізує клієнт; додаткового API-методу для підтвердження не вводиться.

### API-10 — `GET /dashboard`

- **Призначення:** зібрати дані дашборда для поточного користувача. [ДЖЕРЕЛО: US-05, AC-10.3]
- **Auth:** обов'язкова. **Path/body:** немає. **Query:** `today` — календарна дата користувача `YYYY-MM-DD`, обов'язкова [ДЖЕРЕЛО: `requirements.md` розд. 5.4; назва параметра — ПРОПОЗИЦІЯ].
- **Успіх `200`:**

```json
{
  "overdue_cases": [
    { "id": 4, "title": "Отримання довідки", "status": "SUBMITTED", "deadline": "2026-11-08", "created_at": "2026-11-01T09:00:00Z", "updated_at": "2026-11-01T09:00:00Z" }
  ],
  "upcoming_cases": [
    { "id": 17, "title": "Отримання закордонного паспорта", "status": "PREPARING", "deadline": "2026-11-23", "created_at": "2026-11-09T15:30:00Z", "updated_at": "2026-11-09T15:30:00Z" }
  ],
  "due_reminders": [
    { "id": 8, "reminder_date": "2026-11-09", "text": "Підготувати документи", "case_id": 17 }
  ]
}
```

- **Правила:** `overdue_cases`: `deadline < today` та статус не `APPROVED/REJECTED/CANCELLED`; `upcoming_cases`: дедлайн від сьогодні до `today+14` **включно**, лише некінцеві; без дедлайну — не потрапляють у жодну з цих колекцій; `due_reminders`: `reminder_date <= today`, незалежно від статусу справи. Порожні колекції → `[]`.
- **Помилки:** `401`; `422` — `today` відсутня або некоректна.
- **Дата «сьогодні»:** сервер не визначає часову зону сам, а бере `today` із запиту (робоче припущення `requirements.md`, розд. 5.4 і розд. 6, п. 18; OPEN-C02 закрито). Результат вище наведено для `today=2026-11-09`.

## 5. Реєстр маршрутів для інших US (поза дев'ятьма деталізованими методами)

Це **не нові вимоги й не погоджений HTTP-контракт**. Це перелік операцій, які доведеться формалізувати для покриття решти існуючих user stories. Поки для них не визначено body, відповіді й статуси, **не можна стверджувати, що API всього Release MVP спроєктовано повністю**.

| Область | Попередні маршрути [ПРОПОЗИЦІЯ] | Вимоги |
|---|---|---|
| Чеклісти | `GET/POST /cases/{case_id}/tasks`, `PATCH/DELETE /cases/{case_id}/tasks/{task_id}` | US-09 / AC-09.1–09.5; початковий стан задачі — `requirements.md`, розд. 6, п. 6 |
| Документи | `GET/POST /documents`, `GET/PATCH/DELETE /documents/{document_id}` | US-07 / AC-07.1, 07.3 |
| Файли документів | `POST /documents/{document_id}/file`, `GET /documents/{document_id}/file`, `DELETE /documents/{document_id}/file` | US-07 / AC-07.4–07.6; заміна — R-13; байтова межа — `requirements.md`, розд. 6, п. 8 |
| Зв'язок документа зі справою | `PUT/DELETE /cases/{case_id}/documents/{document_id}` | US-07 / AC-07.2; AC-03.6 |
| Установи | `GET/POST /institutions`, `GET/PATCH/DELETE /institutions/{institution_id}` | US-08 / AC-08.1–08.5 |
| Зв'язок установи зі справою | `PUT/DELETE /cases/{case_id}/institutions/{institution_id}` | US-08 / AC-08.6; F-19 |
| Нагадування | `GET/POST /reminders`, `GET/PATCH/DELETE /reminders/{reminder_id}` | US-10 / AC-10.1–10.5 |

**Файли:** допустимі формати `PDF`, `JPG/JPEG`, `PNG`, `DOCX`, `TXT`, `XLSX`, `P7S`, розмір не більше **5 МБ** — це задано джерелом. Коди `413` і `415` визначено в §1.2; заміну файла задає R-13, окреме видалення — AC-07.6. Окремого погодження ще потребують спосіб `multipart/form-data` і точна байтова межа «5 МБ» (`requirements.md`, розд. 6, п. 8). При створенні документа разом із файлом **не допускається часткове створення документа, якщо завантаження не вдалося** [AC-07.4]. Тому майбутній `POST /documents` повинен підтримати **атомарне** створення метаданих разом із необов’язковим файлом (або еквівалентний погоджений механізм з rollback); `POST /documents/{document_id}/file` призначений для додавання файла до **вже існуючого** документа; повторний виклик замінює файл [R-13]. Це не свідчить про погодження конкретного multipart-контракту.

## 6. Питання на погодження (Decision Log для API)

| ID | Проблема | Робоча пропозиція | Статус |
|---|---|---|---|
| **OPEN-C01** | AC-06.1 дозволяє вільну зміну статусів; матриця 6×6 забороняє частину переходів і вихід із кінцевого статусу | Тимчасово застосувати формалізовану матрицю; після рішення синхронно виправити AC або матрицю | **Закрито (0.2):** AC-06.1 виправлено за матрицею, додано AC-06.3–06.4 |
| **OPEN-C02** | «Сьогодні» за локальною календарною датою користувача vs припущення про UTC | Не вводити приховану timezone-логіку; погодити джерело дати/таймзони | **Закрито (0.2):** query-параметр `today` в API-05 і API-10 (`requirements.md`, розд. 5.4) |
| **OPEN-C03** | При видаленні справи нагадування залишаються, а технічний спосіб розриву зв'язку не затверджений | Установлювати `reminders.case_id = null` транзакційно | **Закрито (0.2):** R-10 |
| **OPEN-C04** | AC-04.7 вимагає пов'язані документи, задачі й установи в деталях справи | Узгодити вкладені `tasks/documents/institutions` або ресурсні endpoint-и | **Закрито (0.2):** вкладені масиви в API-06 |
| **OPEN-C05** | Формат і механізм токена, TTL не визначені; при виході токен не відкликається [F-22] | Bearer token; формування токена й TTL — в ADR (крок 8) | Потребує підтвердження |
| **OPEN-C06** | Чи вводити `/api/v1`, єдину JSON-форму помилки, політику `401/404/409/422` | Прийняти пропозиції розділу 1 | Потребує підтвердження |
| **OPEN-C07** | Початковий стан нової задачі (`requirements.md`, розд. 6, п. 6); точна байтова межа файла (розд. 6, п. 8) | Не приписувати неузгоджену поведінку API; заміна файла (R-13) і кратність установ (F-19) уже визначені | Потрібні рішення перед розширенням |

### Що саме команда має звірити перед позначкою «agreed»

1. `requirements.md` і цей контракт послідовно використовують `title`, `deadline`, `status`, `case_id`, `owner_id`; у JSON статуси — **UPPER_SNAKE_CASE**, а `Preparing` з UI — лише відображувана назва.
2. Для `POST`, `GET`, `PATCH`, `DELETE` визначено path/query/body, позитивні результати, релевантні помилки й наслідок невдалих запитів.
3. `PATCH` не плутає відсутнє поле та `null`; невдала зміна атомарна; статус має окремий маршрут.
4. `404` не розкриває чужих даних; `409` для бізнес-конфлікту не підміняє `422` для невалідного enum.
5. Жодна можливість Mini Issue Tracker (наприклад, `GET /users` з двома тестовими агентами чи пріоритети issues) **не була механічно перенесена** на PaperTrail.
6. Розбіжності OPEN-C01–OPEN-C07 обговорені з командою та зафіксовані у `decision_log.md` **до** впровадження відповідних маршрутів.
